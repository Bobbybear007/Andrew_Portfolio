Project Overview

Commonwealth Online is an ongoing attempt to add native-feeling multiplayer functionality to Fallout 4. Where the game was built around a single player and a single simulation, the project lets multiple players connect to a server while each of them keeps running their own copy of Fallout 4. Remote players are represented inside each client's game and kept in sync through the Commonwealth Online networking system.

That is a much bigger problem than it first sounds. Fallout 4 was never designed to have more than one player character, and almost none of its systems expect to communicate over a network. Adding multiplayer means building the systems the engine does not already provide: collecting and transmitting player movement and state, spawning and updating a remote player in each client's world and managing connections as they come and go.

The project has to do all of this without replacing the Fallout 4 executable. Commonwealth Online works alongside the game through F4SE and CommonLibF4, reaching into the running Creation Engine while remaining an external modification. The goal is not to build a separate game that feels Fallout-shaped, but to make multiplayer feel like part of Fallout 4 rather than something bolted onto the side of it.

Some of the recurring challenges we work through are synchronizing player movement, representing remote players, networking game state, managing connections and disconnects and integrating multiplayer safely with engine internals that were never written to be replicated.

Building Multiplayer Into Fallout 4

At a high level, Commonwealth Online sits between the single-player game and the other players in a session. Each client keeps running its own Fallout 4 simulation; the mod layer is what collects the relevant state, sends it across the network, and applies what it receives back into the local game.

Each player continues running their own Fallout 4 simulation while Commonwealth Online synchronizes the relevant multiplayer information between connected clients.

The architecture has changed a lot during development. Early work relied on simpler relay-server setups to prove that players could see each other at all; over time the project has moved toward a more robust C++ networking architecture, with a dedicated server and shared networking code between client and server. The system is deliberately not presented as a finished, fully authoritative MMO-style implementation. Much of it is still evolving as we learn where the engine pushes back.

Client Architecture

F4SE Integration

Commonwealth Online integrates with Fallout 4 through F4SE (Fallout 4 Script Extender) and CommonLibF4. That lets the project interact with the running game, reading and writing state and hooking into engine behaviour, while remaining an external modification rather than a patch to the Fallout 4 executable itself. Working this way keeps the approach compatible with a normal modded install, but it also means every interaction has to respect how the engine already expects to be used.

Player Synchronization

The client collects relevant player state and transmits updates across the network. That includes systems relating to position, rotation, player state, movement and the representation of remote players. Because updates arrive at intervals rather than continuously, remote movement needs to be smoothed rather than applied raw: clients interpolate between the states they receive so other players move naturally instead of snapping between network updates.

Remote Players

Every connected user has to be represented as an actor inside each other player's local world. This is where the single-player assumptions of the Creation Engine become most obvious: Fallout 4 is built around one player character, and it has no built-in concept of a second human-controlled actor appearing, moving, and disappearing on command. Representing remote players means creating and managing those actors, driving them from network data and cleaning them up when players disconnect.

Server Architecture

Rather than treating one player's Fallout 4 game as the entire multiplayer authority, Commonwealth Online includes separate server software. The project has evolved away from early relay-server experimentation and toward a dedicated C++ server architecture, which gives us a single place to own connections, sessions and the shared state that clients agree on.

A dedicated server owns connections and sessions, with shared networking and core code used across the client and server where it makes sense.

The server side is built in modern C++ and uses GameNetworkingSockets as the transport layer. Because the server is its own program, it can be hosted and run independently of any particular player's game. It can manage the awkward parts of running multiplayer, holding sessions open, tracking who is connected and handling players joining and leaving, without dragging the whole simulation into one client.

This is the engineering problem I find most interesting: deciding what the server actually needs to know, what stays local to each client, and how to keep the two honest with each other when the game underneath was never designed to be networked.

Multiplayer UI

Commonwealth Online is not only backend networking. It also includes custom multiplayer interfaces integrated into the Fallout 4 experience, so players can find and join a session without leaving the game. These cover areas such as multiplayer menu integration, connecting to servers, server and session information and player/session details, along with social functionality and pause-menu multiplayer options.

Designing this UI is partly a technical exercise in extending the game's menus, and partly a design exercise in making a multiplayer layer feel like it belongs in a game whose interface was written for one player.

Technical Challenges

A few of the engineering problems that shape how the project is built.

Multiplayer in a Single-Player Engine

Fallout 4 assumes there is one local player and one local simulation. Adding multiplayer means adapting systems that were never designed to communicate over a network, without breaking the single-player experience they were written for.

Synchronization

Players need to see remote movement and actions consistently, without flooding the network or producing visibly unstable motion. Smoothing and update frequency both matter here.

Game State

Not every piece of Fallout 4's state should simply be transmitted between players. The project has to decide what stays local, what is shared, what is replicated and what may eventually become server-authoritative.

Engine Integration

The multiplayer layer has to interact safely with Fallout 4 and F4SE while working around the limitations the Creation Engine imposes on external code.

Networking

The networking architecture needs to handle latency, disconnects, reconnects and the creation and removal of remote players without destabilising the game.

Development Evolution

Commonwealth Online has gone through several architectural iterations. Each one taught us something about where the engine resists being networked.

  1. Early Prototype

    A basic multiplayer proof-of-concept and the first attempts at player synchronization.

  2. Multiplayer Foundation

    Remote players, connection management and improved synchronization.

  3. Dedicated Server Work

    Separate server software and hosting workflows, moving the session out of any single client.

  4. Networking Rewrite

    Movement toward a modern C++ server architecture using GameNetworkingSockets.

  5. Current Development

    Expanding synchronization, improving reliability, multiplayer UI, server infrastructure and deeper game integration.

Current State

Commonwealth Online is still under active development. It is experimental and it is not yet intended to provide a completely seamless Fallout 4 multiplayer experience. There are areas that work, areas that are in progress and areas that are still being figured out.

Current development is broadly focused on synchronization reliability, multiplayer game-state systems, server architecture, UI integration, player and session management, broader gameplay synchronization and improved hosting and connection infrastructure. I would rather be clear about what is unfinished than present the project as further along than it is.

Project Philosophy

Commonwealth Online is intended to remain free. The mod, the server software and the core functionality are not something we plan to lock behind a paywall. The project exists because we want to play Fallout 4 with other people and we want anyone who feels the same to be able to do it too.
